# 我在项目中用 OpenCode 构建前端 Agent 研发体系

# 一、问题的起点：AI 不是不会写代码，而是没有"工程身份"

过去几个月的时间，几乎每个研发团队都经历过同一个循环：需求来了，打开 AI，输入「帮我实现这个功能」，生成代码、本地跑、报错、补 Prompt、再生成。短期看，速度确实快了；但项目跑上半年之后，问题集中爆发——代码风格逐渐失序、架构边界被悄悄越过、AI 的修改半径无法预测、技术债以肉眼可见的速度累积。

把锅甩给「模型能力不够」其实并不公平。真正的根因是：我们一直把 AI 当作一个高级代码补全工具，而软件研发从来不只是写代码。一个完整的交付链路至少包含需求理解、方案设计、架构决策、编码实现、测试验证、Code Review 等环节，把这一整条链路压缩进一句 Prompt，本身就是反工程的。

所以我在项目里做了一件事：不再训练 AI 写代码，而是为 AI 设计工作流，把它从单一的 Coding Assistant 升级成一个具备分工协作的 AI Software Team，承载这个体系的工具是 OpenCode。关键是免费!!!

# 二、核心思想：Artifact 驱动，而非 Prompt 驱动

传统 AI Coding 的协作链路是这样的：

用户 → Prompt → AI 记忆 → 代码 → 人工修 Bug

问题在于上下文完全沉淀在对话里——不可审计、不可回溯、不可复用。一旦换个会话窗口，所有「共识」就消失了。

我的做法是把协作介质从「聊天上下文」迁移到「工程产物」：

Requirement.md → Plan.md → Architecture.md → Code → Review.md

每一个阶段都落到一份具体的、可审计的 Markdown 文件上。Agent 之间不靠「记住上一句话」协作，而是靠可审计的软件工程资产协作。这一点借鉴了真实研发团队的运作逻辑——产品不会口头把需求传给开发，而是写成 PRD；架构师不会把设计塞进微信群，而是落到设计文档。

# 三、Agent 角色拆分：让每个 Agent 只做一件事

在真实团队里，产品不直接写代码，架构师不直接提交 PR，测试不负责设计方案。但很多团队让一个 AI 同时扮演产品、架构、开发、测试、Reviewer——结果就是 AI 不停地推翻自己。

每个 Agent 都有明确的输入、输出和边界，其中最关键的两个是 myPlanner.md 和 myBuilder.md，它们承担了「思考」和「执行」的分离。

# 四、myPlanner.md：先思考，再编码

绝大多数 AI Coding 翻车的根因，是需求一来就直接写代码。Planner Agent 的存在，就是为了在第一行代码出现之前，把模糊需求转化成可执行的工程方案。它的输入是用户原始需求、产品描述、Bug 反馈；输出是一份结构化的 Implementation Plan，包含五个固定模块。

需求复述是第一道关卡。Agent 必须先用自己的话写出「这个需求真正解决什么问题」，避免「用户说 A、AI 实现 B」的经典错误。目标拆解则把一个大需求拆成页面、组件、状态、API、数据流五个维度，让后续 Builder 有清晰的实施单元。

技术选择这一节我刻意要求 Agent 不仅回答「为什么选 A」，还必须回答「为什么不用 B」。例如选 Zustand 而不用 Redux，理由要写清楚：当前项目已经在用、学习成本低、状态粒度匹配；Redux 的引入成本高、当前规模不需要。这种带有反方论证的决策，是降低后期返工的关键。

最后是风险分析和 DoD 验收标准——前者强制 Agent 提前思考性能、兼容性、异常流程、弱网、边界情况；后者明确「什么情况下算完成」，避免无尽的来回修补。

Planner 最重要的原则：不写代码，只负责降低错误决策的概率。

# 五、myBuilder.md：执行者，而非开发者

Builder Agent 的定位非常克制——根据设计执行实现。它读取 Plan、Architecture 份产物，然后在严格约束下编码。

它被禁止做三件事：自己改变架构、随意新增依赖、扩大修改范围。Builder 不思考「应该怎么设计」，只回答「如何按照设计正确实现」。这种角色分离看似牺牲了灵活性，但换来的是修改半径可控、变更可预测、回归风险低——这对长期项目而言比短期效率重要得多。

# 六、AGENTS.md：给 Agent 建立工程边界

很多团队的问题不是 AI 不会写，而是 AI 不知道团队规则。我在项目根目录建立 AGENTS.md，作为整个体系的 Agent Runtime Policy。

维度内容示例
代码规范import 顺序、命名规范、Component 结构、CSS 规范
行为限制禁止修改无关文件、禁止删除测试、禁止扩大需求范围
项目约束国际化扫描仅限指定文件、依赖白名单、目录权限

有了这份文件，AI 不再按照训练数据里的「平均代码风格」工作，而是在当前团队的具体规则下工作。这是从「通用 Coder」走向「团队成员」的关键一跃。

# 七、完整研发 Pipeline 与项目结构

把上述角色串起来，完整的交付链路是这样的：

Feature Request → Planner Agent → Architect Agent
                → Builder Agent → Test Agent → Reviewer Agent
                → Documentation Agent

我自己对应到 OpenCode 的项目结构：

project
├── AGENTS.md // 代码生成规范
├── .opencode
├── agents // 智能代理
│   ├── myPlanner.md // 任务拆解
│   ├── myBuilder.md // 任务自行并执行测试用例
├── commands
│   ├── feature.md // 新增小功能
│   └── review.md // 代码审核
│   ├── fix.md // 修复BUG
├── skills // 常用专业技能
│   ├── i18n.md // 国际化处理
│   ├── code-analysis.md // 解读代码

.agent/ 目录是整个体系的「工程产物中心」——所有需求、方案、架构决策、Review 记录都沉淀在这里，既是 Agent 的协作介质，也是团队的知识资产。

# 八、真实开发体验的变化

以前接到「商品管理」这种需求，流程是：问 AI → 生成代码 → 发现影响了多个模块 → 人工排查 → 反复打补丁。

现在只需要一行命令：

@myPlanner 商品管理 XXX 具体的需求

系统自动跑完整条流水线：Requirement 拆需求，Planner 设计方案，Architect 圈定边界，Builder 实现，Reviewer 检查。每一步都有产物、有审计、有边界，人介入的位置从「修 Bug」前移到了「评审方案」——这才是真正意义上的研发提效。

# 九、从代码生成到工程智能

AI 时代真正拉开差距的，从来不是「谁让 AI 写代码更快」，而是谁能设计更可靠的 AI 软件生产流程。代码生成只是能力，Agent Workflow 才是生产力。

未来的软件工程师不会消失，但工作重心会迁移：从亲手写每一行代码，转向设计一个可以稳定交付的软件智能系统。myPlanner.md 和 myBuilder.md 这样的文件，会逐渐取代过去的 ESLint 配置和脚手架模板，成为团队最核心的工程资产。
